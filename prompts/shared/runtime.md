# Shared runtime

Apply this runtime before the selected Helm workflow in Claude Code, Cowork, or Codex. Run only that workflow; reading another command or a repository document does not invoke it.

## Package and workspace

The package root is the directory containing this runtime, `rules/`, `skills/`, `guides/`, and `.claude-plugin/plugin.json`. Resolve bundled links from the actual file being read. On Claude, `${CLAUDE_PLUGIN_ROOT}` identifies the loaded package; elsewhere derive the root from the selected SKILL.md's location. Never guess a cache version or substitute another installation when a required resource is missing.

The consumer workspace is the user's selected project and working tree. Keep it as the working directory for Git, builds, tests, and generated output. Read workflow and archive-step instructions from the package; read and write project files, `.claude/rules/`, `.helm/`, `.archive/`, and recovery files in the consumer workspace. A consumer's similarly named `guides/`, `prompts/` or `rules/` directory is not a substitute for packaged workflow resources.

Exclude `.helm/`, `.archive/`, `.claude/helm/` and `.claude/{refactor-log,test-log,normalize-log,legal-manifest}.json` from source discovery and history/diff rendering under the safety rules' **Operational Helm state** policy. Read messages/metadata and changed names/status first; exclude protected paths before rendering supporting patches. Owning-workflow access and the narrow exceptions below do not authorize state migration.

The Git rules' **Local work and ship method** section owns common local/publication boundaries and setting meanings; each selected workflow owns its branch eligibility, preparation and completion requirements. Use the [local-edit Git procedure](content-sync.md) when directed. Verify workspace and action capabilities under the safety rules' **Host capabilities** section before dependent operations.

**Narrow publication-state exception:** ship may probe no-follow metadata for exact canonical/unsupported archive roots and relevant Git-native rewrite metadata. For normalize evidence, ship follows the [local handoff procedure](normalize-handoff.md), which owns the bounded read-only discovery and its fallbacks; normalize alone registers locators. These hints grant no live-ledger access, broad private search, force update or backup. Before opening an archive bundle obtain its explicit inspection selection, then use only the packaged canonical root/schema/seal procedure and update only that selected bundle's publication journal/receipt. A normalization continuation reads only identified private recovery/graph/map evidence and relevant committed bookkeeping delta as opaque provenance; never its live ledger. Conflicting required candidates need reconciliation rather than silent precedence/fallthrough. Other ledgers remain opaque. Missing procedures block dependent work. Missing normalize proof prevents verified-history/release-correspondence claims; ship may instead use its explicitly approved [replacement-and-backup procedure](history-publication.md#replacement-without-normalize-evidence) for branch publication, without creating normalize locators or proof. Source maintenance and agent switching grant no locator, recovery or operational-state access.

**Narrow review-anchor exception:** only log/manifest validating an invalid marker may load [review-anchor recovery](review-anchor.md). It permits bounded read-only locator/map/object evidence for that marker, never live normalize state or publication. This is lazy caller-owned recovery, not runtime discovery; other workflows and source maintenance gain no access.

**Narrow backup-retention exception:** Ship may use [backup registration and retention](normalize-retention.md) for bounded read-only discovery and registration of an approved verified fallback remote backup before replacement. Its separate `ship-backups` pointer is never Normalize proof. Only Ship's successful final stage records verified completion and automatically retires eligible recovery folders and matching pointers/checksums, keeping three completed backups total across Normalize and fallback types per clone plus unfinished/dependency-required proof. No new approval pause, live-ledger access, broad home search, source-maintenance cleanup or cleanup after failure follows.

## Project instructions and configuration

Read the consumer's active project instructions and the bundled [Git rules](../../rules/git.md), [safety rules](../../rules/safety.md) and [writing rules](../../rules/writing.md). Respect project-specific and adopted rules. Loading them installs or weakens nothing and adds no writing dependency to an existing copied Git/safety pair.

Use the Git rules' **Project memory and configuration** procedure before dependent writes. `{memory_file}` means its resolved knowledge/configuration owner, not an importing wrapper. `{instruction_file}` means the active host root entry: `CLAUDE.md` in Claude; `AGENTS.override.md` when present, otherwise `AGENTS.md`, in Codex. A package's contributor instructions are never consumer memory. Do not change global client settings.

Only log/adopt perform their declared instruction-layout writes. Follow their owner reconciliation, bootstrap, override, source-project/installation and external-reference guards; resolving a missing owner does not create it. Other workflows preserve ownership when saving an authorized setting. Log does not convert rule installations; adopt installs only reviewed local copies, with independent additions separately accepted. Design and Interaction are optional and are not loaded universally by this runtime; respect them when adopted or otherwise selected by project instructions.

## Mechanical helpers and temporary scripts

This boundary adds no checklist, report, benchmark or helper-code review to routine execution. Maintainer tests/builds and website code have separate purposes; they are not consumer prerequisites.

- Use native Git/search/file tools for straightforward work and reviewed packaged helpers for recurring mechanical parsing, filtering, exact comparison, counting, retrieval or graph/filesystem operations. Helpers must replace manual work with less total context/tool overhead or more reliable results. Agents own interpretation, priorities, selections, approvals and workflow/state/publication decisions.
- During Helm execution, create no helper, probe or orchestration programs: no inline interpreter code, executable heredocs, generated shell programs, temporary script files or modified/copied replacements for installed helpers. Use existing native command calls/pipelines with ordinary search/query arguments and fixed reviewed helpers; no custom processing functions, loops or evaluation blocks. Host-required tool-call syntax may only invoke existing operations with data arguments, not implement helper logic. JSON requests/maps are data. Explicitly selected project code/tests/configuration remain workflow outputs under their own write/execution gates; do not disguise an ad hoc helper as an output. If an existing capability cannot do the job, report the limit instead of creating a workaround. Helper development belongs in a separately authorized coding task. Use bounded inputs and compact structured output; add no cache, tracking framework, gate, dependency, model or permission change.
- Preserve exact data across tools. Transport timestamps/identities as text; preserve unknown JSON numbers losslessly or retain original bytes. Use Git HEAD/status and focused content checks before edits, without routine inode/nanosecond inventories or workspace fingerprints. Owning state digests/recovery proof remain required. Reuse valid evidence, batch projections and retrieve only necessary records without reducing promised coverage.
- Correct one evidenced invocation/argument or lossless data-delivery mistake in an existing read-only tool call and retry it once, with unchanged identity, baseline, scope and permissions. This permits no code creation/editing, parser repair or installed-helper patch. Pause downstream work meanwhile. Denied actions, failed mutations, invalid state, access/whole-input limits and genuine mismatches still stop; never replace evidence or round a baseline. If verification remains unavailable, stop with a safe check-specific reason. Suppress secret-bearing raw errors, not the reason, and lead with the current workflow outcome.

## Prerequisites and stops

Check prerequisites before gated work, including substantive reads. Establish route eligibility using minimum permitted instruction/workspace/scope/path/Git metadata before source inventories, history, rule comparisons, findings tables or plans. Check later state, isolation, verification and destination requirements at their first permitted entry, never by eager forbidden reads/execution. Preserve normalize's coordination order and lazy owner access. A documented clarification/reconciliation uses only its gate's evidence, then waits; question delivery and existing equivalent-method choices grant no bypass.

An established required gate failure **stops the selected workflow**, including further reading, advisory output, planning, other approved units, writes, finalization and return checkout. Report the blocker, scope, prior results and needed resolution; preserve actual files/index/refs and successes. Only minimal safe readback of an uncertain attempted outcome may follow, without retry or cleanup. A defective read-only probe has only the bounded correction above. An unanswered question pauses the workflow until an actual answer arrives.

Explicitly requested supported read-only/report-only routes use their own prerequisites from the outset, never as automatic fallbacks. Authorized bootstraps, selected documented methods, missing scan baselines, findings, unselected optional work and accepted partial/draft outcomes retain their owning choices; none waives safety, ownership, state, approval or verification. Add no bypass choice, approval stage or gate record.

## Questions and authorization

Before the first human question, read [Question mechanism (QM)](question-mechanism.md) once: use its form/routing/answer contract and the current host's relevant capabilities; load detailed alternatives/recovery or other-host/MCP reference material only if needed. Each workflow's Question points map owns when to ask, prerequisites, exact choices, approval scope and exits. QM grants no state access, execution, new approval stage or permission to change client modes/settings. No question means no QM setup question or capability probe.

Preserve workflow confirmations and exits under the safety rules' **One authorization standard** and QM answer rules. Do not pre-approve execution/publication tools through skill metadata.

`Write` and `Edit` refer to full replacement and a targeted patch respectively; use the host's equivalent file tools while preserving those semantics and the workflow's read-back verification.

## Execution and evidence reuse

Use one transient working snapshot for the selected scope, without a new checklist/report. Investigate further only for an unmet coverage requirement or a concrete missing fact that changes a decision. Proceed when evidence is sufficient; disclose nonblocking uncertainty once. Missing required facts block dependents.

At each step, batch its independent permitted reads/probes and required references, then reuse unchanged instructions, facts and immutable-object content. Return necessary fields, bounded source and exact decision evidence. Retrieve unread material after truncation; summaries never replace required content or coverage. Conditional loading does not make a reference optional.

Before writes refresh relevant HEAD/index/worktree, instructions/configuration, destination, remote refs, protection/checks and request state. Freshness alone requires no new semantic review. Changed/unknown evidence invalidates dependents; never refresh a rejected lease into permission. Readback after success/uncertainty is mandatory. Reuse crosses no unresolved source, policy, package or approval change.

Reuse passed checks only while actual inputs, configuration, environment and policy match; exact-SHA requirements still need that SHA. Do not repeat suites or run model/site/client checks merely because another file/phase was visited. Preserve scope, coverage, approvals, state/recovery and verification; add no speed mode, automatic model/effort change, timing promise or extra question.

## Delegation and checkpoints

Workflows that explicitly name delegation, or a user's explicit delegation request within the caller's existing scope, may use the host's available read-only workers when invocation and active instructions permit. Substantial refactor/test Full scans and large log investigations benefit from bounded assignments; other named independent investigations may delegate proportionally. Small/ordered work, especially ship and adopt, defaults to the parent; this is not a blanket ban on permitted unusually large independent read-only work. Queue within actual available slots and any caller ceiling, never using concurrency as a total coverage cap. Without delegation cover the same scope sequentially or report incomplete. Pass actual package/consumer paths, source identity, exact scope/depth, applicable instructions/overrides, policy context and safety restrictions explicitly; workers may not inherit them. Follow the investigation contract only when the caller loads it, not as runtime autoloading or a no-scan prerequisite. Fresh context is not a filesystem sandbox.

On Codex, the parent owns code edits, Git mutations, provider operations, ledgers, and state writes. Permitted read-only local Git object/metadata inspection is investigation, not mutation; caller/tool restrictions still apply. Workers return findings plus inspected identities/depth, unresolved edges and unread remainder, not a finding count as proof of coverage. They do not execute project code, perform Git mutations or provider operations, read operational state, start another workflow/worker, answer user questions or update aggregate state. Parent reconciliation uses exact identities and permitted own history; available read evidence cannot prove semantic understanding. Process editing clusters and waves sequentially. Keep Claude's existing wave behavior, but never promise a fresh-session mechanism the host cannot provide; continue from the recorded checkpoint in the current session or report the precise resume point.

Refactor/test load the parent's [read-only ledger helper](ledger-helper.md) only when an existing permitted own record or an authorized write needs validation/retrieval. Its single initial index read can validate and return a bound page; use a separate check only for validation-only work. The reference owns runtime availability and exact-data preservation. Missing records, explicit source-only/report-only routes, workers and unrelated commands gain no helper/setup prerequisite. Invalid data and package defects retain their blockers; helpers add no writer, state access or authority.

Refactor/test/normalize/legal load the [project-state procedure](project-state.md) only at their eligible owning-state entry. Archive and ship's selected archive backup use the [canonical bundle procedure](../../guides/archive.md#resolve-one-archive-root). The safety rules' **Operational Helm state** section owns canonical paths, owner-only access, unsupported-input preservation and sequential writers; each workflow owns checkpoint evidence and approvals.

Update complete client packages and start fresh sessions. Never write consumer results into the installed plugin.
