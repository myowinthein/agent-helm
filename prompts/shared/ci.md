# Shared CI gates

Apply only to the action requested by the invoking workflow. Reading this procedure does not run checks or authorize publication.

Use the caller's QM map: wait/recheck versus leave pending is Single; any permitted concrete publication-for-checks action is Review. Local-only callers still offer no push/PR, and no answer waives a required result.

## Determine the applicable gate

Record the action, source branch and exact source SHA. Inspect project CI configuration, active instructions and applicable provider protection/review requirements. Absence of `.github/workflows/`, or a non-GitHub remote, does not establish that CI is absent. Unknown policy/access is a capability gap, not a successful or not-applicable check.

Apply that uncertainty to the gate actually required for the action. Lack of provider access alone does not invent a pre-integration remote gate for a permitted direct local integration when no project/known applicable policy requires one. Provider requirements that constrain remote publication remain enforced at that publication; a permitted local merge is never permission to bypass them or claim CI passed. If a declared/applicable requirement itself cannot be resolved or verified, keep that action pending.

- **Integration:** applies to selected base/main integrations; source publication and core own-target PR creation enforce their actual pre-publication/API requirements without waiting for future review/merge. Require remote checks that project policy or provider protection requires before actual integration. `ship-method: pr` ends at verified review handoff and cannot auto-merge. Direct shipping does not acquire a pre-integration remote gate merely because a pipeline exists: when no policy requires that gate, applicable local checks may permit local integration. An explicit required remote gate under either ship method must pass; local tests never substitute for it.
- **Promotion:** configured/applicable CI must succeed for the exact published source SHA/ref before any selected environment merge/push or PR handoff. Ordinary ship may source this from a feature, main/env helper or current branch; use the actual approved published ref, not older main checks or another target result. A published base/release source selected in the conversation retains that exact source. Local editing commands never promote. Optional targets are independent, never a chain. A target PR is a review handoff: later PR/merge-result CI and review remain pending/not awaited, not prerequisites merely to open it. Actual required source/API-publication checks still apply. Record not applicable only when evidence establishes that no configured/applicable CI exists, never as a fabricated pass.

## Verify required results

Use an authenticated supported provider interface. On GitHub, verify repository access and inspect all applicable workflow runs, required check runs and commit status contexts for the exact SHA, with pagination. Do not use a fixed recent-run limit as proof of complete coverage. Other providers require equivalent pipeline/check evidence. Git transport access alone does not establish API access; do not install tools, change credentials, or alter client settings automatically.

Every applicable required result must be complete and successful. Failed, cancelled, pending, missing, unknown, stale or truncated results block the action. A skipped check is acceptable only when policy establishes it is not required. Ignore results for another SHA and superseded attempts. Recheck the branch tip and required results immediately before the gated mutation; a changed tip invalidates prior evidence.

An unpublished branch may have no remote results. If remote CI is required, offer a separately confirmed branch push (describing the exact ref and consequences) or a review/manual handoff, then wait for that exact SHA's checks. Reuse a caller's concrete publication question/approval for this same exact branch push rather than asking twice; ship's exact source-publication choice can supply it. Publishing for checks does not silently change the ship method. Local-only commands report the unmet dependency without offering a push/PR; publication is a separate ship action. Respect branch-trigger filters: a push alone does not prove the required pipeline will run. If checks cannot be obtained on the supported path, leave integration pending rather than bypassing the policy.

When a gate is blocked, report the source SHA, non-secret reason, completed operations and pending targets. Stop/skip the affected action, or offer exactly two choices such as `Wait and recheck` and `Leave pending`. Only a later verified success unblocks it; timeout, host approval, environment selection, or a `Promote anyway` answer cannot waive required CI. A post-publication block leaves the published source intact, with no environment mutation or branch cleanup.
