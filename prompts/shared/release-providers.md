# Release provider procedures

Use ship's QM map for user decisions: Input for missing repository/channel facts, Single for supported provider alternatives, and Review for exact PR/MR or hosted-release writes. Provider permission prompts remain separate from workflow authorization.

Read when ship requests provider inspection, CI evidence, an approved PR/MR handoff or hosted release. These procedures do not invoke another workflow or grant writes. Apply the caller's `ci.md`, instruction ownership, exact-SHA policy and confirmations. Ship alone loads this guide; other workflows retain their existing CI procedures.

## Identity and capability binding

Bind one `{push_destination}`, `{provider_host}`, `{repository}` and repository/project ID from ship's selected push URL plus authenticated read-only repository metadata. Parse SSH/HTTPS and configured SSH aliases safely; strip credentials from reports. Do not guess enterprise/self-managed providers from a `github.com` substring or route credentials to an unverified hostname. Resolve ambiguous aliases/custom hosts explicitly. Release/CI/hosted-release APIs bind to the intended release project, not an ambient CLI default. Every core/optional PR separately binds the caller's exact published feature/helper/base/env source and selected target. A fork feature is an explicit separate-source/target mapping, never implicit authorization for a second Git push; optional direct target destinations require their own concrete binding/approval.

GitHub uses an existing authenticated `gh` or equivalent supported API on the confirmed host; GitLab uses existing authenticated `glab` or equivalent API. Check CLI availability before auth queries and verify repository access, not just login. Use explicit host/repo/project selection in every call, with safe argument/query encoding, pagination and no credentials/debug headers in output. No automatic install, login, token creation, certificate bypass or client/global configuration edits. Git access is separate from API access; an unavailable provider step is pending/manual, not CI absent or a successful release.

Bitbucket, Azure Repos, Gitea/Forgejo and unknown hosts retain the explicitly approved Git path with provider-specific manual PR/release handoff. Available equivalent authenticated CI evidence can satisfy the shared gate; no dedicated PR or hosted-release writer is provided for them here. Do not translate GitHub flags into incompatible provider APIs or promise tested end-to-end support.

## PR/MR handoff

Ordinary pr shipping publishes the caller's reviewed source first. A feature keeps its existing source and chooses main/environment targets optionally; no helper or self-PR is required. Main/env uses one established ship/* source into its own hosted current branch, then that SAME helper for optional targets. Bind the published source repository/project/ref/SHA and every target repository/project/ref independently, including explicit fork mappings; never substitute older hosted main/env or another target's merge result. All requests are independent and may integrate before a pending main PR. Reuse/prove a pending helper before creating one, and never open same-repository same-ref requests. Release-metadata PRs remain separately reviewed; never tag a pre-merge candidate. An existing published source selected during target review keeps its exact published-base-to-env ref pair without creating a helper.

For a fork feature, establish the intended upstream PR target from explicit developer/project evidence, confirm it when not already authorized and verify authenticated read-only host/repository/project identity and access separately from the source push binding. Resolve the actual selected target main/master or confirmed environment and its protection/review/check policy, then assess the full feature-to-target diff against its real current tip. A changed target/base invalidates the affected diff/approval. Search/read requests in the target repository/project, checking the explicit source identity; GitLab creation uses the verified source project endpoint with the verified target project ID. No cross-host/unrelated-project guess or push to upstream is allowed. If either binding/base/policy cannot be established, leave a precise manual handoff. For optional environment targets verify the intended environment-owning project and exact approved feature/helper/env/base source mapping, rather than assuming every head is main or an ambient fork. An upstream PR grant is never a grant to push upstream.

Before an API write show the exact source/target, reviewed changes, title/body, configured permitted integration method and known PR/preview/notification effects. Obtain concrete creation approval or reuse an unchanged plan/selection explicitly describing that PR creation; a generic command or branch name is not consent. Applicable local/source/publication checks remain required, but do not wait for future PR CI/review/merge to open a review handoff. Never request auto-merge, execute a provider merge/update-branch API, enable source deletion or weaken protection. Preserve permanent main/environment branches, existing human PR content and project templates. Inspect required PR templates/conventions before preparing the body; unsupported requirements leave a precise manual handoff.

Search all applicable open PRs/MRs with complete pagination for the exact source/target repositories and refs. Read back head SHA against the caller's approved published tip before reuse or creation. Reuse one matching open request without rewriting it; multiple matches or mismatched identity/head need reconciliation. A formerly merged request may precede genuinely new source changes: first inspect current target inclusion and the new reviewed diff. Already-integrated output is a no-op; a new approved range may have a new request. Never silently reopen a closed request, duplicate a matching open one or treat a historical merged request as the present open handoff.

For original main/env helper discovery, inspect associated pending optional requests as well as its own-target history. A merged own-target PR does not retire a still-applicable helper used by open target PRs. Keep that proven source/scope and skip its completed own request; do not switch head refs and create parallel same-work requests. A new helper is justified only after candidate absence is established; inaccessible or ambiguous evidence is not absence. Reviewed original-branch/source context and actual graph/content must establish association, never a branch prefix alone.

- **GitHub:** use the authenticated host-bound `gh` API or equivalent with explicit target repository. List `GET repos/{owner}/{repo}/pulls` filtered by source head and target base, then inspect the exact PR. Create with `POST repos/{owner}/{repo}/pulls` and structured `title`, `head`, `base`, `body`, plus supported explicit source-repository identity when needed for a fork. Use `head: {published_source_ref}` and `base: {selected_target}` for ordinary optional requests; a main/env core own-target request uses its one helper as head and the original branch as base. Explicit existing-source promote retains `head: {base_branch}` and `base: {environment}`. Do not use a CLI that offers to push an unapproved branch/fork or silently chooses another repository.
- **GitLab:** bind source and target numeric project IDs/hosts. List the applicable project merge requests with `state=opened`, `source_branch`, `target_branch` and pagination, then verify both project IDs and the head SHA. Create through `POST projects/{source_project_id}/merge_requests` with structured `source_branch`, `target_branch`, `target_project_id`, `title`, `description` and `remove_source_branch: false`. Use the caller's exact published feature/helper/env/base source and selected target for ordinary handoffs; explicit existing-source promote retains main/master as source and the selected environment as target. Inspect the permitted squash/merge policy without mutating settings or promising the requested strategy overrides project enforcement.

Supply all multiline text as structured input or a safe request/body file, never shell interpolation of source/notes. Verify the created/reused request through a separate read: actual URL/number or IID, open state, source/target host/repository/project/ref and head SHA against the approved published source. A head change during the API operation preserves the actual request but leaves the affected result pending reassessment, not silently successful. Check available mergeability/policy evidence without polling for completion; conflicts or unknown/pending checks are reported honestly. Existing source-deletion/auto-merge instructions that threaten retained permanent branches require reconciliation rather than silent reuse or settings changes. Attach every created PR/MR to the task when the host supports PR attachments. A URL or API exit alone is not verification. On uncertain API outcomes inspect actual request state before retrying; access denial or failed lookup is not proof of absence. Preserve successful feature publication or earlier target PRs on failure and stop dependent actions.

A verified open request completes that handoff. Ordinary ship may next handle only already reviewed independent optional targets using the SAME source, never await or merge the first request. Release-metadata handoffs remain terminal with no optional targets. Ship never approves/merges requests, waits for future review/CI, updates source branches from targets, deletes branches or claims deployment. Every request tracks its source feature/helper/main/env ref until integration: read back/report the observed SHA and disclose that pushing fixes updates every open request sharing it. Do not create a duplicate or new helper just to update an existing request; verify old/new source history/content and normal fast-forward eligibility first. Previously merged targets need a new explicitly selected request for genuinely new commits. For explicit existing-source promote, an older exact snapshot cannot silently widen to newer main or gain a snapshot helper. Missing tools/access or unsupported hosts leave exact source/target/manual steps and a pending result. Do not automatically install tools, log in or create credentials.

## GitHub CI and release

For a required gate, inspect repository policy, all applicable workflow runs, check runs and status contexts at the exact SHA on the relevant branch/tag, using authenticated host-bound API queries with complete pagination/current attempts. Typical reads are `GET repos/{owner}/{repo}/actions/runs?head_sha={sha}`, `GET repos/{owner}/{repo}/commits/{sha}/check-runs`, and `GET repos/{owner}/{repo}/commits/{sha}/statuses`, plus applicable branch protection/rules. Filter by the required context/ref/event, not merely a green run sharing the commit. Resolve expected but missing checks, external statuses and superseded reruns. Required unavailable/unknown results block; policy-established optional/skipped results do not become fabricated passes. Recheck source tip and results immediately before the gated action.

Before hosted release creation, verify authenticated repository identity and the published exact tag object/peeled commit. Read `GET repos/{owner}/{repo}/releases/tags/{encoded_tag}` to detect existing/uncertain writes. A verified matching existing release is reused/reported; differing notes/channel or identity needs explicit reconciliation, never an automatic edit. A 404 is absence only after repository access is established; denied access/network ambiguity is unknown.

Show the exact notes/title/channel/latest policy and any release-event automation in the caller's hosted-write approval. Infer prerelease from the SemVer prerelease field, not build metadata or a substring. Stable maintenance releases are not automatically global latest; set the reviewed latest choice explicitly. Use `--prerelease --latest=false` for prereleases, `--latest=false` for non-latest maintenance/other releases and `--latest` only for an approved latest stable release.

An illustrative command, with each placeholder safely supplied as an individual argument and notes from a real safe file, is:

```sh
gh release create {release_tag} --repo {provider_host}/{owner}/{repo} --verify-tag --title {reviewed_title} --notes-file {notes_file} {reviewed_channel_flags}
```

Do not allow automatic tag creation from the default branch, use moving `--target` to repair a missing tag, interpolate raw notes in shell, or attach assets implicitly. When CLI version/API capability lacks a required flag, use a verified equivalent interface or report blocked. After success or an uncertain response, read back the same release's tag, publication state, channel/latest fields, URL and remote tag target. Existing draft/private state is not a published release. Failed/unknown outcomes require same-tag inspection before retry; never cut a new version or overwrite a published release as recovery.

## GitLab CI recipe

Use authenticated `glab api --hostname {provider_host}` with explicit encoded project endpoints, or an equivalent supported API. Resolve `GET /projects/{encoded_path}` and bind its numeric project ID/path/host to the push repository. Read applicable project, protected branch/tag, merge/review and external-status requirements; metadata that cannot establish a declared gate leaves it unknown. Do not assume every protected branch forbids every direct push or that API unavailability means no protection.

For an exact source `{sha}`, read **all pages** of `GET /projects/{id}/pipelines?sha={sha}`. Do not filter only `status=success`, sample recent pipelines, use a latest-by-branch helper or `scope=branches/tags` as complete evidence. Match each required branch/tag/MR ref and pipeline `source` to the action. An MR merge-result pipeline has its own SHA; a passing MR or unrelated tag pipeline does not establish a passing published base/environment SHA.

For every applicable current pipeline inspect `GET /projects/{id}/pipelines/{pipeline_id}`, paginated `GET /projects/{id}/pipelines/{pipeline_id}/jobs` and `GET /projects/{id}/pipelines/{pipeline_id}/bridges`. Resolve current versus retried jobs/attempts (include retried history when needed), job status and `allow_failure`, with applicable external commit statuses from `GET /projects/{id}/repository/commits/{sha}/statuses`. Follow required bridge/downstream project/pipeline IDs and inspect their own exact source relationship/results; the root list excludes child pipelines by default. Use `source=parent_pipeline` where appropriate or explicit downstream IDs, not an assumption that the root list covers everything.

Map the expected validation jobs/checks from actual included CI rules and project policy. Inspect manual/blocked/skipped/pending/failed/cancelled/scheduled/unknown requirements; `allow_failure` or aggregate pipeline success alone cannot waive an independently required check. Distinguish required pre-promotion validation from deployment jobs whose execution is a separate approved action; reading a gate never triggers/retries a pipeline, approves a manual job or deploys. If policy, included config, downstream access or expected pipeline creation is unavailable, leave the affected gate pending. No relevant pipeline after publication is not proof of no CI; verify rules/filters and report missing evidence.

Record source/ref, pipeline/job IDs/URLs and current results. Recheck the Git source/destination refs and the applicable pipeline attempts before mutation, using `ci.md`'s passed/not-applicable/pending rules. Remote CI required by policy needs an approved supported publication/review path; it is not replaced by local tests, nor is a new remote gate invented for an permitted unprotected direct action.

## GitLab hosted release

GitLab releases use an existing tag, but `glab release create` may otherwise create a missing tag or **update** an existing release. Ship must first verify the exact published tag and project identity, then read `GET /projects/{id}/releases/{encoded_tag}`. Reuse a matching release, explicitly reconcile disagreement, and distinguish a real authenticated not-found from inaccessible data. Honor CI-owned release generation before considering a write.

GitLab's Releases API has no GitHub-style prerelease/latest flags; latest lookup uses `released_at`. Identify the channel in the reviewed name/notes and disclose actual provider semantics before approval. Never promise that a prerelease/maintenance release will be excluded from global latest, fake dates to force ordering, or pass GitHub flags. If the project's required channel/latest policy cannot be met, offer Git-only/manual handoff and leave hosted creation pending rather than silently publishing it as stable/latest. No artifact/package-registry upload, milestone closure or release catalog publication is implied.

Prefer a create-only structured request through the existing authenticated `glab` API interface, binding the confirmed host and numeric project. Write a safe request body with only reviewed `tag_name`, `name` and `description` (and any separately approved existing policy fields), **omitting `ref`**, assets and milestones. An illustrative invocation, with each placeholder supplied as a safe individual argument, is:

```sh
glab api --hostname {provider_host} --method POST projects/{project_id}/releases --input {reviewed_request_file}
```

Check installed CLI/API capability and tag identity immediately before the call. With no `ref`, a missing tag must fail instead of being recreated; POST creation must conflict rather than update an existing release. Stop/reconcile unexpected disappearance/change or a concurrent release, never repair via default-branch HEAD. A manual `glab release create` handoff must explain its automatic create/update behavior and use supported `--no-update` / `--no-close-milestone` safeguards; it is not the strict missing-tag-failure writer above. Never automatically update/delete a release to recover from conflict.

After success or an uncertain response, read back the same release, tag name, commit.id, name/description, released/upcoming state, `_links.self` and actual remote tag objects. Check against `{release_sha}` and the approved notes/channel; future/upcoming is not already published. Account for concurrent CI creation by inspecting/reusing the verified matching result. A URL/CLI exit alone does not prove identity/completion. Failure leaves Git publication intact and a same-version retry/manual handoff.
