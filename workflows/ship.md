# ship

Publish reviewed work through one workflow: inspect pending work, use verified history-replacement or private archive procedures when applicable, handle selected branch targets and offer an approved release on ready main/master. Publication, PR handoff, integration, release and deployment remain separate outcomes. Never publish registry packages or upload release assets automatically.

## Question points

Use [QM](../prompts/shared/question-mechanism.md) at the existing gates below and in the selected publication/provider helpers; ask only when their conditions hold.

| Point | QM form |
|---|---|
| Missing source/role/destination/product/stream/version/private-evidence identity | Input or Single for actual candidates; never infer scope from divergence or a branch prefix. |
| Conflicting special routes or prepared-candidate status/resume | Single; archive inspection itself uses its existing Review before bundle access. |
| Base preparation commit, exact source push/helper/PR creation and target action | Review of each concrete operation, reusing only sufficient same-action approval. |
| Optional targets | Multi with None / Finish; Single Yes/Skip for one target. Target selection precedes exact action Review when not already concrete. |
| Release / Skip / Choose another version / relevant Use 1.0.0 | Review of the shown release plan; custom/initial version → Input, then refresh Review. |
| No configured test framework, supported sequential publication or hosted release | Review with the existing explicit proceed/leave-pending choices; failed/unavailable required checks remain blockers. |
| History publication and archive payload/receipt publication | Separate Review of the exact selected protocol, fixed expectations and effects. |
| Archive destination/privacy facts, preservation/cleanup, portable copy | Input for safe identity/paths; Single for retention route, Multi for independent candidates, then Review of exact effects. |
| CI wait/recheck versus pending and missing resume operations | Single for wait/pending; Review only for missing mutations lacking valid approval. |

## Before starting: policy and permissions

Apply the shared runtime and resolve effective instructions and `{memory_file}`. Resolve only the settings/capabilities needed by the selected work: `ship-method` (`direct`/`pr`, default pr; retired-key leftovers follow the Git rules' stop guard), independent `git-merge-strategy` (default squash), applicable base identity and provider policy. Freeze/recheck invocation policy; never write settings or migrate instruction ownership. Read `{package_root}/prompts/shared/ci.md` and `release-providers.md` before their gates. Independent optional targets have no tier ordering. Pass developer requests and answers unchanged, never as shell code.

Initial assessment uses safe local Git and authenticated read-only provider evidence. It performs no fetch, optional index refresh, checkout, project hooks/checks, commits, file/ref writes or publication. Suppress executable Git helpers and lazy fetching where supported; unavailable reads remain unknown. A request to run ship approves inspection, not pushes, history replacement, backup, metadata changes or tags. Present concrete effects at the existing approval gates and reuse still-valid same-action approval. No new setting, state file, ledger or recovery writer is introduced.

## Step 0 — Identify pending work and choose the safe publication procedure

Inspect the actual repository/current branch, relevant local/remote refs, existing PRs, known release candidates and explicitly identified retained work. Build a transient per-action assessment: new source work, existing handoff, selected target work, pending history publication, prepared archive backup, unreleased product changes, unfinished release or proven no-op. Unknown remote/history/provider evidence is not absence of work. Use Step 7's evidence and continuation rules before creating a helper, release commit or tag.

### Detect special publication work without reading unrelated state

- **Normalization:** use a normalize handoff visible in the trusted conversation or a developer-identified private recovery path. Metadata-only checks of exact Git-native filter-repo markers and relevant ref/reflog evidence may flag a possible rewrite; they prove neither Helm ownership nor publication scope. Divergence alone never selects history replacement. When a relevant trace lacks the private evidence, ask for that run's recovery path before dependent publication; do not search private directories, reconstruct a map or read normalize's live ledger. Validate repository/source/old/new ref identity and the complete map/bundle under [history publication](../prompts/shared/history-publication.md). Ambiguous, missing or overlapping runs require reconciliation, not force or ordinary-push fallback. No trace is proof of absence: an unexplained divergence still blocks ordinary publication. Normalize retains its existing private handoff; a fresh session may need the developer to identify it.
- **Archive:** probe only no-follow path metadata for the canonical `.helm/archive/` and protected unsupported `.archive/` roots, never their contents during generic discovery. A candidate is not proof of preparation. Offer **Inspect this archive for backup / Leave pending** before opening its bundle, reusing explicit known backup intent. After selection, load [archive publication](../prompts/shared/archive-publication.md) and its canonical validation/old-root stop guard. Only this selected continuation may read/update that one bundle's journal/receipt. An incomplete or invalid selected archive returns to archive preparation or remains pending; never publish its payload through ordinary shipping as a shortcut. A proven completed backup reports its result without replay. Archive publication is terminal: no ordinary push, branch fan-out, version or tag follows it.
- If archive and rewrite evidence both apply, or their source/destination/provenance conflicts, show the candidates and resolve the intended independent work before opening additional inputs or publishing. Never silently chain backup and source publication. A deliberately unrelated candidate can remain pending only after the ordinary included history is independently reviewed and safe; ignoring a trace never waives a publication gate.

After a selected history publication is fully verified, retain its exact published refs, deliberate local-only refs and proven old/new release correspondence in working context. Do not push that history again through the ordinary path. Offer optional targets only from a specifically reviewed verified published current source under Step 6; then assess release eligibility. A failed/blocked selected history action stops dependent targets/releases while preserving successes. No PR can substitute for replacing published IDs.

### Ordinary work, existing candidates and completion

For ordinary work, reuse proven existing source/helper/PR identities and perform only missing actions through Steps 1/6. Detect a pending or integrated release-metadata candidate before routing its metadata-only delta as application work. A uniquely proven candidate uses Step 7's same-version continuation; an open metadata PR is already handed off and stops tagging. Ambiguous identity or unrelated ahead application work requires reconciliation, not another bump or code PR.

An already-published current tip still permits Step 6's optional targets: selected environments may be behind even when the source needs no push. Do not treat an optional target's different tip as authorization; show only applicable concrete actions and obtain selection/approval. An unchanged proven selection is reused. After verified ordinary publication/targets or a proven source no-op, assess the release stage below. A core PR may be followed by explicitly selected independent target PRs, but is never awaited/merged. Pending main code/metadata PRs prevent a release of that work.

- Work successfully published on ready main/master: offer the release plan with **Release / Skip release**, including changes with no automatic version bump; version choice remains explicit.
- No source push needed, but published main has unreleased product changes or a proven incomplete release: offer the new release plan or only missing same-version actions. A previous tag need not exist: assess a first release from complete scoped history. A published tag by itself is not a new release opportunity; already-complete/skipped optional hosted output is not automatically recreated.
- No source publication, applicable selected target update, unreleased product work or required incomplete release: report **Nothing to publish or release** and exit without a question, empty PR/commit/tag or state write. Open review handoffs are reported as pending, not as nothing to do. Unknown evidence is a pending limitation, not this no-op result.

## Step 1 — Establish scope, capabilities and core publication

Perform a read-only inventory first. Resolve the actual repository, base and current branch role from project/developer evidence, not prefixes. Confirmed roles are base, feature and environment; detached, unconfirmed environment candidates, ambiguous or unsupported maintenance/release/bot roles block ordinary publication writes rather than being routed to main. A branch that is the actual base uses the base route even when it also deploys production. Record `{original_branch}`, current attached branch/HEAD, index/tree, ongoing Git operations, shallow/missing history and required capabilities. No repository/HEAD or ambiguous base blocks dependent writes, never initializes Git. Product/stream selection is required for release, not speculative versioning of every ordinary source push.

Resolve actual fetch and **push** URLs, upstream/configured push behavior and credential-free host/repository/ref identity. Do not assume origin/fetch URL or an ambient provider repository. Bind exactly one source push destination; ambiguous/multiple push URLs need resolution. Bind each optional target's actual repository/destination separately in its reviewed action, never infer authorization to push to another remote. A fork feature PR additionally verifies the intended upstream target and its actual main/environment refs, access and policy; source publication grants no upstream push. Unavailable provider access is not proof of absent protection, CI or PRs.

Inspect applicable project checks/signing/protection, branch/tag/PR-preview deployment triggers and CI-owned version/tag/release behavior. Respect real restrictions on bypassing main or publishing environment branches even though Helm now permits explicitly chosen edges. A required PR blocks direct target publication and offers a separately reviewed PR alternative, never silently switches method or bypasses protection. Unknown required policy blocks the affected gate. Source/target publication grants no release approval and must not duplicate CI-owned version/tag/release automation.

### Safe worktree, remote baseline and publication evidence

When assessing publication diffs/history, read `{package_root}/prompts/shared/investigation-evidence.md` for the existing exact scope only; no-investigation paths gain no prerequisite. Default to parent review for ordered publication work. Unusually large independent read-only history analysis may delegate when permitted, returning exact reviewed commit IDs, full-message/needed-diff evidence and unresolved remainder; parent alone handles provider operations, ref/source decisions, approvals and execution. Reconcile exact required IDs/changes with the pinned publication/release range, never just counts or a recent sample; do not add a full-code audit, generic Full/Gap choices or an operational ledger.

Every mutating route requires clean safe index/tree and no in-progress merge/rebase/cherry-pick/revert before dependent actions. Inspect path metadata first: pending operational Helm state blocks without opening it; secret-bearing/non-template env/private-key changes and unverifiable content block publication without unsafe diffs. Never stash, reset, discard, absorb unrelated staged work or merely exclude unsafe paths and continue dirty.

On base only, retain the existing explicit **Commit reviewed safe changes / Stop here** preparatory logical-unit choice, with exact staging/content verification; it grants no publication/tag/PR approval. Feature/env edits must be safely committed through normal development first. Committed work can still be unfinished: review the entire included range/diff, not just today's changes, and stop unready/excluded work.

For writes, describe needed narrow fetch/history completion before performing it. Preserve tags, unrelated refs and remote configuration; no pruning/forced tag replacement. Compare actual advertised source/target refs. No ordinary force, automatic divergent merge/rebase, reset or conflict repair. A behind-only clean branch may be safely fast-forwarded under policy and reassessed; otherwise leave manual reconciliation. Detect reviewed squash/rebase equivalence before calling old IDs new work: do not republish equivalent patches or create another PR to fix local divergence. Pin `{source_sha}` to the complete reviewed current tip after preparation and capture remote expectations. Recheck before every dependent mutation; later target results never replace this source.

Before core publication show the source SHA, exact destination/refspec, full included changes, applicable checks and known triggers, and obtain concrete approval or reuse same-action approval. Inspect existing PRs that use the source: pushing review fixes updates **all open PRs sharing that source**, not only a newly selected target. Disclose those known effects before approval. A previously merged PR/branch does not receive later commits automatically; new changes need an explicitly selected new target action. Verify actual refs and provider results after success or uncertainty before retry. Required deferred/unavailable/failed checks remain pending, never green.

### Core direct publication

For base, feature and confirmed environment alike, publish only the exact reviewed current branch tip to its intended same-role remote ref with `--no-follow-tags`, after applicable pre-publication checks/approval. Never merge into main, merge main into the current environment or push another branch merely to finish the core. An already published matching tip needs no duplicate push; verify and report it. Remote-ahead/divergent or unrelated local-ahead work requires reconciliation, never force. Verify the actual remote ref against the approved SHA/containment plan. A new ref needs its creation/triggers described explicitly.

After core success, bind `{published_source_repository}` and `{published_source_ref}` to that verified current-branch destination at `{source_sha}`, then offer Step 6 optional targets. Selecting none skips target writes; an original-main invocation still assesses release availability, while a feature can finish at verified branch publication without integration into main. Source push/deployment effects remain explicit; a push is not verified deployment. Core failure or unresolved publication outcome blocks dependent target work.

### Core PR publication and helper reuse

For a **feature**, the existing feature ref is the source: approve/push/verify it exactly as above under source-publication policy. No helper or self-PR is needed, and a main PR is not automatic. Proceed to optional main/env target selection; none still means the feature was published successfully. `ship-method: pr` controls integration-target updates, not the source push needed to propose them.

For **base or confirmed environment**, propose the reviewed current work through one `ship/*` source ref into the hosted current branch. Never open same-repository same-ref main-to-main/env-to-itself PRs, push that permanent target directly, or reset/rewind/rebase/cherry-pick the original branch to move work. The original branch stays at its current tip.

Resolve the complete target diff and whether work is already integrated before creating anything; reviewed inclusion/equivalence creates no empty own-target PR or new helper. Inspect retained optional requests below before concluding a helper is unnecessary. Only if no established applicable helper/optional handoff remains may an already-published current branch bind its verified repository/ref/SHA as the optional source. Unreconciled squash/rebase divergence still blocks dependent publication; equivalence does not authorize silently changing `{source_sha}`.

Before making a helper, inspect applicable open requests and explicitly identified retained run/source evidence with complete pagination. Reuse a uniquely established helper for this original branch/work and exact own-target repository/ref; its name prefix alone is not ownership. Verify actual PR identity, graph/content, source/target tips and all open requests sharing that helper. An existing source at `{source_sha}` needs no repush.

Updating it for review fixes requires its observed published tip/history to be fully included in the reviewed current source and a normal fast-forward; show the entire delta and effects on every shared-source PR. Helper-only reviewer commits absent from local source, conflicting work, multiple/uncertain candidate helpers, denied lookup or a closed-unmerged request require reconciliation/identification, not a new helper, overwrite, force or silent reopening. A source already integrated with different IDs needs deliberate original-branch reconciliation before another publication.

If the own-target PR merged but associated optional PRs remain open, keep that proven shared helper for the still-applicable reviewed work; do not replace it with hosted main/env and create parallel same-work target PRs. Verify the old source/scope against the current plan, review any eligible fast-forward helper update and its shared-PR effects, and skip the already-integrated own-target request. A changed/ambiguous scope needs explicit reconciliation, not an automatic source swap. Historical merged/closed requests alone never establish a new pending helper.

Only when the absence of a matching pending helper/request is established may ship create an unused `ship/changes-{YYYYMMDD-HHMMSS}` at the exact reviewed tip, with a numeric suffix on collision. Keep enough reviewed original-branch/source context in its PR proposal to support later identification without a new ledger. Do not reuse an unrelated name or create helpers per target. Obtain approval, run applicable checks, push/verify this exact source ref, then create/reuse/read back the matching own-target PR/MR through the provider guide unless its reviewed content is already integrated. A failure after source publication preserves it and reports missing PR/API work; later runs recover that identified source rather than duplicating it.

Freeze `{published_source_ref}`, `{published_source_repository}` and `{source_sha}` for optional targets. For a new/pending helper, every optional PR uses **that same helper**, not the older hosted current branch.

Example: local main has C above remote P; helper(C)→main and helper(C)→staging both propose C, independently. Staging may accept it before main or even if main rejects it. Show this in the plan and obey stronger project restrictions; do not silently substitute P or wait for main's PR to merge.

No PR route auto-merges, waits for future review/CI, updates a source from its target, deletes branches or releases. After an own-target PR handoff, proceed only to the expressly optional independent actions in Step 6 and then report.

### Release readiness and decision

Assess Steps 2–3 read-only once release availability is established; perform Steps 4–5 only after concrete release approval. Require the invocation to start on actual main/master and the current checkout to be that same verified integrated base before metadata/tag mutations. Feature/env invocations finish publication/handoffs without a release offer; never silently checkout main to tag a target result. After optional target checkouts from an original-main invocation, apply Step 8's independent safe-return checks before release preparation; a failed return leaves release pending.

Reconcile local main with the actual intended published base after independent integration. Unpublished application changes must complete source publication/integration first; an open code PR is not release readiness. Stronger protection/review/check policy remains binding. Only the subsequently reviewed direct release-metadata commit is an allowed new base delta within the release route.

Before computing a bump, identify any existing local tag, pending/merged metadata PR, version patch already included in the original code PR, or explicitly identified failed candidate for this product/stream. An open verified metadata PR is already handed off: report and stop. After integration, prove its accepted patch/source on actual published main (including complete content/provider evidence for squash/rebase), then use the **same version**, not another bump/PR.

A partial direct release may retain exactly its proven previously approved metadata-only delta above that integrated code under Step 7; do not resend it through generic source publication or reject it as unpublished application work merely because its push/tag failed. Unrelated/ahead application work still blocks. Do not infer candidate ownership from a branch name, subject or version string alone; ambiguous candidates need reconciliation.

A ready integrated/tag-only candidate needs no empty metadata commit/PR. Show new metadata edits under the ordinary direct/PR policy only when actually needed. Publish/integrate application code first. An aligned main with eligible unreleased work proceeds to the optional release decision without an empty code PR; release files/refs remain untouched until approval. Failed/unknown required checks, unmerged work or unresolved publication prevents tagging. Skipping release preserves published code and creates no persistent decline preference.

## Step 2 — Determine the release baseline and version

For a new release, identify the selected product's canonical version source and exact tag convention. Prefer `.claude-plugin/plugin.json` for a confirmed Helm/plugin product; otherwise inspect existing package.json, composer.json, VERSION or project-declared/tag-derived versioning. Resolve competing sources/independent packages explicitly. Do not add a version field/file to a tag-versioned project or assume incidental manifests are owners. Missing version files permit an explicitly reviewed tag-only release; there must be no undefined staging target or fabricated empty release commit.

Determine the appropriate **published** previous release and its proven reachable or mapped-equivalent boundary for this product and stable/prerelease/maintenance stream. Use complete relevant tag/history evidence and real SemVer parsing, not an arbitrary nearest `git describe` result or the highest global tag. Keep `{previous_tag}` (exact existing ref) separate from its parsed `{base_version}`; do not prepend `v` to an existing tag. Confirm ambiguity, unpublished local tags and metadata/tag disagreement rather than silently picking a winner.

Define `{release_base_sha}` as the peeled previous tag commit when it is reachable from the intended source. If a verified normalization disconnected preserved tags, use only the identified private run's complete old/new map and recovery objects to prove that tag's mapped equivalent, graph/parent continuity and unchanged product tree. Keep `{previous_tag}` and its published object unchanged; use the verified mapped commit as the exclusion boundary and report both identities. Account for multiple runs explicitly; never guess/combine maps or treat absent ancestry as a first release. Missing/ambiguous correspondence blocks release analysis until the evidence is supplied.

Message/ID-only rewriting of already released history is not new product work. Genuine unreleased original work and later approved product changes remain in scope; an empty tree diff alone does not prove a no-op. Proven release/bookkeeping-only overlays do not justify another version. Notes and version analysis use the same validated release boundary, not an unreachable tag's raw range.

Before proposing another bump, recognize evidence of an existing prepared/partly published candidate, such as a local-only release tag or matching release metadata commit ahead of the published baseline. Offer same-version status/resume or Cancel instead of treating it as an ordinary new change. A separate new release requires an explicit choice and a fresh assessment; uncertain tagless identity still follows Step 7 rather than being guessed from HEAD.

A first release uses the full scoped history through `{source_sha}`, with a report of the complete assessment. Never substitute an empty `..HEAD` range. An existing version is an initial candidate, not an instruction to bump twice; ask for the intended initial version. With no version evidence, offer 0.1.0 as a proposal, not an already approved base/release. Missing/shallow history is unknown, not proof of a first release.

Read full commit subjects, bodies and footers for `{release_base_sha}..{source_sha}`, or the explicit first-release history. Reconcile inspected IDs with every commit in the exact scoped release set; unread messages or missing history remain unknown and block dependent version/completion claims. Preserve boundaries/IDs and inspect relevant product changes; do not limit the analysis to `--oneline` or a recent sample. Apply Conventional Commits case-insensitive type/scope handling with the specification's uppercase breaking footer tokens:

- `!` after **any** type/optional scope, or `BREAKING CHANGE:` / `BREAKING-CHANGE:` footer: breaking candidate. For stable versions propose major; for 0.x explicitly resolve whether the project wants a 0.x breaking increment or graduation to 1.0.0.
- `feat`: minor candidate; `fix` or `perf`: patch candidate, with the highest applicable bump winning.
- Other nonbreaking types have no automatic bump. Reverts need context and must not be mechanically cancelled or assumed harmless. Never normalize/rewrite history here.
- Empty unreleased scope: report no new release needed and offer an existing release's status/resume when relevant. Non-bumping, mixed or non-Conventional history: show the uncertainty and offer **Finish without releasing** / **Choose an explicit version**. Markdown/workflow changes can be the product, so do not equate a `docs` label with no user impact or silently discard those changes from review.

Validate **every** proposed/custom version as SemVer, including prerelease/build identifiers and leading-zero rules. Preserve project tag naming; validate the complete tag ref too. Check local and remote collisions before edits and again before tagging/publication. A new release must have an appropriate increase within the chosen stream; build metadata alone does not increase precedence. Resolve prerelease increments versus graduation explicitly. A same version is a resume/status decision, not another release. Lower maintenance versions need their explicitly selected stream, never an accidental downgrade or global latest designation. Typing a version, selecting the 1.0.0 shortcut or choosing custom entry is not release approval.

## Step 3 — Plan release outputs and notes

Prepare a concrete in-run patch for the canonical version and its verified companions, retaining formatting/unknown fields and avoiding dependency churn. For supported npm metadata keep the package version and existing corresponding package-lock/npm-shrinkwrap root version records consistent; do not change dependency versions/integrities or blindly regenerate lockfiles. Do not assume `npm version` is a harmless edit: it can run lifecycle scripts and create commits/tags. For other declared companions use a verified narrow edit or block that affected release with an explicit repair handoff. Do not insert optional version fields or edit independent packages speculatively.

For plugin releases, update the matching local marketplace entry's existing version when present, after verifying product identity and an unambiguous matching entry. Absence of the file or optional version field is not permission to invent metadata. Conflicting/duplicate identity or version declarations require resolution. Update only identified current **own-product** README version mentions; preserve dependency/minimum versions, historical examples/pinned URLs, frontmatter, custom content and review markers. Respect existing changelog/release-tool ownership; propose only requested or established changelog updates, not a competing new file.

Build reader-facing release notes from the same frozen source range: relevant breaking changes/migration guidance, features, fixes, performance and public security/relevant non-CC changes, without inventing claims or publishing private vulnerability details. A release metadata commit is not a new feature. Never use `v{previous_tag}`, a feat/fix-only grep or moving HEAD for the notes. Show notes in conversation before approval; prepare any approved API/file input outside tracked output, through stdin or a structured body. Never interpolate commit text into shell code.

Show one release-only plan: product/stream, integrated source and previous tag/range, exact proposed version/tag, metadata diff, notes, push repository/refs, method, channel/latest behavior, applicable checks/protection, CI-owned actions and capability/deployment gaps. Offer **Release**, **Skip release**, **Choose another version**, plus **Use 1.0.0** only when relevant (at most four). Changed/custom versions return to the exact plan. Skip/cancel changes no release files/refs; preserve/report any separately approved prior commits.

The explicit go-ahead covers only the described metadata commit/PR or integrated tag/base publication. Hosted release creation keeps its own exact offer/approval. No environment or other target selection follows release, even after successful tagging; later target work is a separately reviewed action within a subsequent ship invocation. Reuse valid approval; material content/source/version/target/destination/effect changes require refreshed review. Auto-commit, tool permission, defaults and timeouts are not consent. A declined release proposal leaves files/refs unchanged and reports remaining evidence without checks or writes merely to complete the proposal.

## Step 4 — Prepare and verify the final release tree

For a new release, recheck the source, effective owner/policy, destination and clean index/tree. If the approved metadata patch is nonempty under pr (or an explicitly selected required-PR route), create an unused `ship/release-{version}` source branch at the verified integrated base, with a suffix on collision, and apply only that patch there. Otherwise apply the approved patch on the permitted base. Branch creation occurs only after exact reviewed ship scope, never in editing commands. A resume candidate uses the same validation/tag prerequisites for missing actions without reapplying metadata, bumping or creating another release commit.

Run the project's established formatter/linter and full release test suite, plus configured required type/build/metadata checks. Use actual project commands and safe existing tools; do not install tools, introduce new scanners or run publishing/deploy lifecycle scripts merely because a check is missing. With no test framework, explicitly ask whether to release without test validation; a configured but failed/unavailable test or required check blocks release and cannot be waived as absent. A request to defer testing leaves affected release/publication pending, not green.

Verify the final version/companion metadata, README/changelog/notes and exact diff. Formatter changes outside the approved release patch require reviewed scope approval; unrelated code fixes return through normal integration, not an implicit release-metadata scope expansion. Run the full required gate on the intended final tree after formatting/edits, ordering checks to avoid redundant reruns. Hooks or later source changes invalidate that evidence: inspect the new content and rerun the required gate. Skip a full rerun only for an established metadata-only change with applicable metadata validation and explicit evidence that source/check inputs are unchanged. Never tag unverified content based on tests from before the release edits.

Stage literal approved paths only, inspect the **complete** index and ensure no unrelated staged content. If files changed, commit `chore(release): bump version to {version}` under the release approval; otherwise a tag-only release needs no empty commit. Verify actual commit contents/tree and hooks against the reviewed output before tagging.

If a metadata source branch was required, publish its exact verified tip through the provider PR/MR handoff after concrete approval, verify/reuse/read back the PR, then finish with no tag, merge, environment promotion or wait. Preserve that branch and version identity for later same-version resume after integration.

Otherwise pin `{release_sha}` to the verified integrated base commit. Recheck tag absence and create the approved annotated tag, honoring required signing policy/capability rather than changing settings. Verify the exact tag object and peeled target. On failed checks/commit/tag, preserve actual edits/index/commit/tag state, stop dependent publication and report how to inspect/resume the same candidate.

A release-metadata PR/MR is a terminal handoff through required review, with the same source push/verified PR procedures as features. Never tag a pre-merge commit assuming squash/rebase preserves its SHA. After independent integration, resume the same version at the proven integrated base SHA and reassess changed content/checks before tagging. A resume of a still-open metadata PR reports that handoff without merging or waiting. Direct shipping blocked by required PR policy offers this explicitly reviewed path, never changes the method silently. Tag-only publication on an already integrated base creates no empty metadata PR.

## Step 5 — Publish and optionally create a hosted release

Before any publication recheck exact local commit/tag objects, remote branch/tag advertisements, policy and approval, accounting explicitly for verified own release commits/tags in the expected snapshots. Unexpected remote/source changes invalidate the pending plan. Enforce any required pre-publication checks through the supported review/check path; an unprotected `direct` release does not acquire an invented remote gate. Where checks can run only after an approved branch/tag push, expose that ordering and its triggers; such publication remains pending validation and never proves later release/promotion gates passed.

Prefer an atomic push of **only** the approved refs to the selected single push destination, with follow-tags disabled. For a new unpublished base commit, use explicit refspecs of the form `{release_sha}:refs/heads/{base_branch}` and `refs/tags/{release_tag}:refs/tags/{release_tag}`, with `--atomic --no-follow-tags`. If the base already contains this approved candidate, publish only the missing exact tag/ref as appropriate; never move a newer base backward. Never push all tags/branches, rely on ambient push defaults, force, or silently publish to a second remote. History replacement belongs only to the verified normalization publication procedure.

If the server specifically rejects unsupported atomic publication, verify actual refs, then offer **Use described sequential publication** / **Leave pending**, explaining the partial-publication risk and branch/tag triggers. Other errors stop for diagnosis, not automatic fallback. Sequential publication pushes/verifies the approved branch first, then the exact tag; a failure stops remaining operations.

Atomic Git refs do not make CI, hosted APIs or deployments atomic and do not suppress duplicate branch/tag pipelines. Network uncertainty requires inspecting authoritative remote refs before retry, not assuming either failure or success. Verify branch containment/tip as planned, annotated tag object and peeled commit against `{release_sha}`; published mismatches block dependent actions and are never overwritten/deleted.

After verified Git publication, offer **Create hosted release** / **Skip** for an available GitHub/GitLab capability, describing its exact tag/repository/channel/notes and known release-event consequences. Reuse explicit approval already covering that exact hosted write. Honor required checks or CI-owned release creation first; if a pipeline creates it, observe/verify that result rather than creating a duplicate. An optional declined/skipped hosted release does not undo Git publication. Missing capabilities yield a same-tag manual handoff; required unavailable gates stay pending. Follow the provider guide's safe create/readback/retry procedure. Do not claim a hosted release or deployment from a local tag/PR or successful preflight.

## Step 6 — Optional targets and an explicitly selected published source

### Select optional targets after core publication

After Step 1 core publication/handoff is verified (or its already-published no-op is proven), offer one QM Multi with explicit **None / Finish**. Do not start target work before this choice. Preserve prior explicit selection of the same reviewed plan without asking again. No candidates means no question; one uses QM Single Yes/Skip, 2–4 use native Multi when supported, more use QM's complete-list fallback. Never truncate or preselect production/main as consent.

| Original current role | Optional targets |
|---|---|
| Actual main/master | Confirmed environments only |
| Feature | Actual main/master and confirmed environments |
| Confirmed environment | Actual main/master and other confirmed environments, excluding itself |

Discover roles from actual configuration/provider/developer evidence, not names alone. Do not offer arbitrary feature/bot refs as destinations. For fork mappings, verify each target's intended repository, refs and policy; a source push/PR target binding never authorizes a second Git destination.
